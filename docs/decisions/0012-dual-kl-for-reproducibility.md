# ADR-0012: Два направления KL-дивергенции для benchmark и проверки воспроизводимости

- **Статус:** Accepted
- **Дата:** 2026-09-05
- **Контекст:** Этап 2 — реализация базовых метрик; Этап 3 — проверка воспроизводимости базовых методов
- **Затрагивает:** Bins, Huffman, Arithmetic Coding; в дальнейшем — все методы, для которых доступно или восстанавливается `Q_stego`

## Контекст

В benchmark specification v0.1 в качестве основной KL-метрики зафиксировано направление

\[
D_{KL}(P_{reference} \Vert Q_{stego}),
\]

где `P_reference` — каноническое эталонное распределение языковой модели на текущем шаге, а `Q_stego` — распределение выбора токена, индуцированное стегометодом.

При реализации и проверке Шага 7.3 выяснилось, что для Bins, Huffman и Arithmetic Coding эта величина в текущих smoke-конфигурациях равна `+inf` на каждом шаге. Причина — support mismatch: существует хотя бы один токен `x`, для которого

\[
P_{reference}(x) > 0, \qquad Q_{stego}(x) = 0.
\]

Одновременно анализ авторской реализации базовых методов Harvard NLP (`NeuralSteganography`) показывает, что для оценки отклонения распределения используется противоположное направление:

\[
D_{KL}(Q_{stego} \Vert P_{LM}).
\]

В этом направлении токены, для которых `Q_stego(x)=0`, не создают бесконечного вклада. Поэтому авторская KL-метрика для тех же методов может быть конечной и именно она пригодна для прямой проверки численной сходимости с результатами исходной работы.

Следовательно, одна KL-метрика не может одновременно выполнять две разные задачи:

1. строго диагностировать потерю support относительно `P_reference`;
2. обеспечивать сопоставимость с авторскими реализациями и опубликованными результатами.

## Решение

В проекте фиксируются **два явно различаемых направления KL-дивергенции**.

### 1. Benchmark-native KL

Основная метрика benchmark v0.1 сохраняется без изменений:

\[
D_{KL}(P_{reference} \Vert Q_{stego}).
\]

Рекомендуемое имя поля:

`kl_ref_to_stego_*`

Назначение:

- строгая диагностика изменения support;
- выявление случаев, когда стегометод полностью исключает токены, допустимые согласно `P_reference`;
- использование в нормализованной benchmark-инфраструктуре;
- сохранение совместимости с уже зафиксированной specification v0.1.

Для этой метрики сохраняются текущие правила:

- без epsilon smoothing;
- если `P_reference(x)>0` и `Q_stego(x)=0`, то KL на шаге равен `+inf`;
- отдельно сохраняется число бесконечных шагов;
- основная единица benchmark — bits/token, если иное явно не указано в спецификации.

### 2. Author-compatible KL

Для проверки воспроизводимости вводится дополнительная метрика:

\[
D_{KL}(Q_{stego} \Vert P_{reference}).
\]

Рекомендуемое имя поля:

`kl_stego_to_ref_*`

Назначение:

- воспроизведение метрики, используемой в авторских реализациях/работах;
- численное сравнение с исходными результатами;
- анализ того, насколько распределение реально генерируемых стеготокенов отклоняется от языковой модели.

В рамках **Этапа 3 «Проверка воспроизводимости базовых методов»** для Bins, Huffman и Arithmetic Coding необходимо рассчитывать обе KL-дивергенции.

При сравнении с конкретной авторской работой дополнительно должны воспроизводиться:

- направление KL;
- единицы измерения (`nats` или `bits`);
- способ усреднения;
- режим temperature/top-k/top-p;
- candidate truncation;
- точность арифметики;
- и другие настройки, влияющие на опубликованное значение.

Если авторская работа использует nats, результат для проверки сходимости должен сохраняться в nats; при необходимости benchmark может дополнительно хранить эквивалент в bits:

\[
KL_{bits} = \frac{KL_{nats}}{\ln 2}.
\]

## Почему не заменяем текущую KL на авторскую

`D_KL(P_reference || Q_stego)` и `D_KL(Q_stego || P_reference)` не являются взаимозаменяемыми.

Первая метрика чувствительна к исключению исходов, которым `P_reference` назначает ненулевую вероятность. Вторая оценивает, насколько вероятностная масса самого stego-процесса согласуется с языковой моделью.

Поэтому замена одной метрики другой привела бы к потере информации и нарушила бы уже зафиксированный контракт benchmark specification v0.1.

## Использование на этапах проекта

### Этап 2

До конца Этапа 2 основной benchmark-метрикой остаётся:

`D_KL(P_reference || Q_stego)`.

Дополнительное направление может быть реализовано заранее технически, но оно не заменяет текущую метрику и должно иметь отдельное имя.

### Этап 3

Для проверки воспроизводимости Bins, Huffman и Arithmetic Coding обязательно рассчитываются:

- benchmark-native `D_KL(P_reference || Q_stego)`;
- author-compatible `D_KL(Q_stego || P_reference)`.

Для оценки **сходимости с авторскими результатами** используется именно то направление, формула, единица измерения и режим агрегации, которые использовали авторы.

### Benchmark specification v1.0

По результатам Этапа 3 рекомендуется решить, следует ли закрепить оба направления как first-class benchmark metrics в specification v1.0.

Предварительное предложение:

- `KL_ref_to_stego` — строгая benchmark-native метрика support/distortion;
- `KL_stego_to_ref` — author-compatible и дополнительная distribution-distortion метрика;
- TVD — симметричная конечная метрика, сохраняемая независимо от обеих KL.

## Последствия

Положительные:

- становится возможна корректная проверка воспроизводимости исходных результатов;
- исчезает неоднозначность термина «KL»;
- бесконечные значения benchmark-native KL не интерпретируются как ошибка;
- сохраняется строгая диагностика support mismatch;
- результаты Stage 3 можно сопоставлять с оригинальными статьями без изменения benchmark v0.1 задним числом.

Отрицательные:

- в schema результатов появляется дополнительная группа полей;
- необходимо явно контролировать единицы (`bits`/`nats`);
- для исторической воспроизводимости может потребоваться отдельный author-compatible режим вычисления и агрегации.

## Решение для реализации

Не использовать общее поле `kl` без указания направления.

Минимально рекомендуемые имена:

- `kl_ref_to_stego_mean_bits`
- `kl_ref_to_stego_median_bits`
- `kl_ref_to_stego_p95_bits`
- `kl_ref_to_stego_max_bits`
- `kl_ref_to_stego_infinite_steps`

и для дополнительного направления:

- `kl_stego_to_ref_mean_bits`
- `kl_stego_to_ref_median_bits`
- `kl_stego_to_ref_p95_bits`
- `kl_stego_to_ref_max_bits`

Для author-conformance runs при необходимости дополнительно:

- `kl_stego_to_ref_mean_nats`
- другие author-compatible агрегаты, если они требуются для точного воспроизведения опубликованной методики.

## Итог

В benchmark необходимо явно различать две задачи:

> **Benchmark evaluation:** `D_KL(P_reference || Q_stego)`.

> **Author-result reproducibility:** рассчитывать также `D_KL(Q_stego || P_reference)` и сравнивать с исходной работой в авторских единицах и режиме агрегации.

Оба направления должны существовать параллельно и никогда не смешиваться в одном поле `KL`.
