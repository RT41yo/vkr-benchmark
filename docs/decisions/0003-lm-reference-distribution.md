# ADR-0003: Граница между LM adapter и каноническим P_reference

## Статус

Принято для реализации этапа 2.

## Решение

Адаптер языковой модели Hugging Face отвечает только за техническую работу с
токенизатором, моделью и KV-cache. Он возвращает полный вектор исходных логитов
для следующего токена. Адаптер не применяет temperature, общий top-k/top-p,
маскирование специальных токенов, сэмплирование контрольного текста или
стеганографическую логику.

`ReferenceDistributionBuilder` отвечает за нормализованный конвейер бенчмарка:

1. привести исходные логиты к FP32;
2. исключить output-only ID и, согласно baseline policy, специальные ID
   токенизатора;
3. применить temperature;
4. выполнить softmax в FP32;
5. применить общий top-k, если он включён, с детерминированным разрешением
   точных совпадений вероятностей по `token_id`;
6. перенормировать распределение;
7. применить общий top-p, если он включён;
8. выполнить финальную перенормировку;
9. передать методам неизменяемый FP32-объект `ReferenceDistribution`.

Основной Torch-путь выполняет FP32 softmax на том же устройстве, на котором
получены логиты, после чего канонический вектор вероятностей переносится на CPU
для слоя стегометодов. Это решение необходимо учитывать при последующем
измерении производительности, поскольку методы этапа 2 получают NumPy-
представление `P_reference`.

## Пространство токенов

Размер выходного пространства модели и пространство ID токенизатора учитываются
раздельно. Наличие ID в токенизаторе определяется по фактическому множеству
значений `tokenizer.get_vocab()`, а не только по условию
`id < len(tokenizer)`. Это делает реализацию устойчивой к потенциальным
непрерывностям в пространстве ID.

Для Qwen3-4B-Base в зафиксированной конфигурации этапа 1 выход модели имеет
151936 позиций, а токенизатор — 151669 отображаемых ID; 267 output-only позиций
всегда запрещены в normalized runs. Special-token ID берутся из
`tokenizer.all_special_ids`, а не из списков, жёстко заданных под конкретную
модель.

## Токенизация prompt

Политика токенизации исходного prompt является явным параметром LM adapter
`prompt_add_special_tokens`. После сверки с `lm_probe/scripts/model_probe.py`
v0.2 для обеих текущих моделей зафиксировано:

```text
prompt_add_special_tokens = true
```

Это решение относится только к исходному prompt. Повторная токенизация
переданного stegotext относится к отдельному транспортному слою и выполняется
по правилам спецификации v0.1 без искусственного добавления специальных токенов.

## Жизненный цикл KV-cache

Для совпадения с вычислительным путём, проверенным на этапе 1, Hugging Face
adapter использует тот же явный набор механизмов:

```text
DynamicCache
+ attention_mask
+ cache_position
+ use_cache=True
+ logits_to_keep=1
```

`prefill(prompt_ids)` выполняет один полный проход prompt и сохраняет KV-cache,
маску внимания, следующую позицию cache и уже вычисленные логиты для первого
генерируемого токена. Вызов `next_logits(state)` без предыдущего токена
возвращает эти pending logits без повторного пересчёта prompt.
`next_logits(state, token_id)` выполняет ровно один autoregressive step через
тот же KV-cache path и возвращает новое состояние.

Encoder и decoder тем самым используют один и тот же конкретный вычислительный
путь.

## Проверка эквивалентности пути этапу 1

Скрипт `scripts/check_lm_adapter.py` дополнительно воспроизводит независимую
копию Stage-1 `model_probe.py`-пути на той же загруженной модели и сравнивает с
LM adapter:

1. логиты сразу после prefill;
2. логиты после одного cached autoregressive step.

Для обоих сравнений требуется точное совпадение tensor values. Скрипт также
выводит фактические dtype/device исходных логитов, точные token IDs prompt,
размеры token space, массу запрещённых токенов и нормировку `P_reference`.
