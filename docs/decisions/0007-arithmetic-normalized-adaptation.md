# ADR-0007: Нормализованная адаптация Arithmetic Coding

## Статус

Принято для этапа 2. Параметры рабочих точек остаются предварительными до pilot sweeps и спецификации v1.0.

## Контекст

Алгоритмический источник для базового Arithmetic Coding — `harvardnlp/NeuralSteganography/arithmetic.py`, зафиксированный reference commit `14e982564aeaf9a33f7b4de440deda2184d17f12`.

Авторская реализация объединяет в одном коде языковую модель, temperature, исключение GPT-2-specific токенов, сортировку, построение вероятностей, finite-precision Arithmetic Coding, BPE-repair и расчет собственных метрик. В normalized benchmark эти обязанности должны быть разделены.

Основное алгоритмическое состояние Arithmetic Coding — целочисленный интервал `[L, R)` внутри `[0, 2^precision)`. На каждом шаге вероятности кандидатов преобразуются в целочисленные ширины подинтервалов. Секретные биты задают точку внутри текущего диапазона; токен выбирается по содержащему эту точку подинтервалу. Общий двоичный префикс границ выбранного подинтервала считается однозначно встроенным, после чего интервал перенормируется и используется на следующем токене.

## Решение

### 1. Метод получает только канонический `P_reference`

`ArithmeticMethod` не имеет доступа к LM, tokenizer, raw logits, KV-cache или common generation policy. Сортировка кандидатов берется из канонического `token_order`.

Авторский параметр `temp` не переносится в Method adapter: temperature уже применена общей инфраструктурой при построении `P_reference`.

### 2. Finite-precision арифметика остается частью метода

Параметр `precision` задает диапазон:

```text
[0, 2^precision)
```

Канонические вероятности FP32 копируются во внутреннее представление FP64 только для преобразования в целочисленные ширины. Сам `P_reference` не изменяется.

В normalized v0.2 `precision` ограничен диапазоном `2..52`: это позволяет точно представлять целочисленные границы при промежуточном FP64-масштабировании. Окончательный диапазон параметра будет зафиксирован после pilot sweeps.

### 3. `top_k` — внутренний параметр Arithmetic Coding

Reference implementation использует `topk=50000` как верхний предел числа токенов, участвующих в целочисленном разбиении. В normalized adapter это `method.params.top_k`.

Он применяется после `P_reference` и принципиально отличается от `generation.top_k` общей политики benchmark.

Перед округлением также сохраняется reference-механизм отсечения вероятностей меньше `1 / (R-L)`, то есть токенов, которые при текущей точности не способны получить один целочисленный пункт диапазона.

### 4. Сохраняется reference-схема округления

После выбора кандидатов их вероятности нормируются на текущую ширину интервала, округляются до целых и накапливаются.

Если округление переполняет диапазон, первый переполняющий кандидат и все менее вероятные кандидаты удаляются. Если после округления остается недостающая масса, она присваивается наиболее вероятному кандидату путем сдвига всех cumulative boundaries на остаток. Это повторяет алгоритмическую логику Harvard `arithmetic.py`.

Полученные целочисленные ширины одновременно задают точное для данной реализации распределение:

```text
Q_stego(token_i) = integer_width_i / (R - L)
```

Поэтому adapter возвращает explicit `Q_stego` с `q_mode=analytic_exact` и `q_source=adapter_exact`.

### 5. Encoder использует перекрывающееся look-ahead окно

Для выбора токена требуется `precision` еще не подтвержденных секретных битов. Однако чтение этих битов не означает, что все они уже встроены.

Encoder поддерживает окно из `precision` битов. После каждого шага payload увеличивается только на длину общего префикса выбранного интервала. Подтвержденные биты удаляются из начала окна, а из `SecretSource` дочитывается ровно столько же новых битов.

Следствие:

```text
secret_bits_read = precision + payload_bits
```

для обычной fixed-carrier сессии. Поэтому `EncoderFinalization.payload_bits` является авторитетным счетчиком полезной нагрузки; количество прочитанных из `SecretSource` битов для Arithmetic Coding больше payload из-за look-ahead.

Это важное отличие от Bins и Huffman и должно быть учтено при следующем E2E-шаге в общем runner.

### 6. Decoder зеркально восстанавливает только подтвержденные биты

На каждом observed token decoder строит то же целочисленное разбиение, выбирает соответствующий подинтервал, восстанавливает общий двоичный префикс его границ и выполняет ту же перенормировку состояния.

В author code последний carrier token имеет специальный flush: decoder выводит полную нижнюю границу для восстановления конечного сообщения. В normalized fixed-carrier режиме этот flush не используется. Мы считаем payload только из битов, однозначно подтвержденных common-prefix механизмом в течение заданного числа carrier tokens.

Source-specific termination/flush будет сохранен отдельно в `author_conformity` реализации на этапе воспроизводимости.

### 7. BPE-repair не переносится

Как и для Bins/Huffman, GPT-2-specific BPE эвристики авторского decoder не входят в normalized adapter. Реальная надежность позже проверяется через общий `TextChannel`:

```text
token IDs -> ordinary text -> retokenization -> decoder
```

## Последствия

- Arithmetic Coding становится первым действительно stateful baseline в общей Method lifecycle архитектуре.
- `bits_consumed` остается корректным per-step полем, но может быть равен нулю на отдельных токенах.
- Authoritative payload задается `EncoderFinalization.payload_bits`, а не числом прочитанных look-ahead битов.
- `Q_stego` доступно точно из фактических integer interval widths.
- Общий runner перед AC E2E нужно слегка обобщить: он не должен предполагать `payload_bits == secret_bits_read`; ожидаемый секрет — первые `payload_bits` битов прочитанного секретного префикса.
