# ADR-0021: Нормализованная адаптация RRC

- **Статус:** Accepted
- **Дата:** 2026-10-09
- **Контекст:** Этап 4, подключение Rotation Range-Coding

## Контекст

Для RRC в качестве основной внешней реализации Этапа 4 зафиксирован репозиторий `ryehr/RRC_steganography` на коммите `dae326259e4fca8bc4fcf460dafdbc0e88a0a71a`. Более ранний коммит `8b6a86a...` относится только к предварительному анализу и не используется как основа проверки соответствия.

Актуальная авторская реализация отличается от ранней версии двумя существенными для бенчмарка решениями: точность `Decimal` вычисляется из длины сообщения, а перед завершением кодирования выполняется обратное воспроизведение процедуры извлечения, чтобы исключить ложное срабатывание условия остановки.

RRC является методом с фиксированной длиной сообщения. В отличие от Bins, Huffman, Arithmetic Coding и Discop, число токенов-носителей заранее не фиксировано: генерация продолжается до успешного завершения range coding, но ограничивается защитным пределом `max_carrier_tokens`.

## Решение

1. Нормализованный RRC получает уже окончательно построенное `P_reference` из общей инфраструктуры бенчмарка.
2. `temperature`, `top-k` и `top-p` относятся к общей политике построения `P_reference`. Внутри нормализованного RRC повторное `top-k` не применяется. Если для проверки авторской конфигурации требуется `top-k`, оно задается через `generation.top_k`.
3. Секрет целиком считывается до первого шага. Длина секрета задается `termination.target_payload_bits`.
4. Отправитель и получатель используют независимые экземпляры PRNG, инициализированные одним `method.key`.
5. На каждом шаге применяется свежий псевдослучайный сдвиг точки секрета внутри текущего интервала.
6. Точность `Decimal` вычисляется как `ceil(bit_length * log10(2)) + precision_margin`; по умолчанию `precision_margin=40`.
7. По умолчанию используется проверенное завершение: перед остановкой отправитель воспроизводит обратные вращения получателя и завершает генерацию только при точном восстановлении исходного целого значения секрета.
8. Декодер не выдает полезные биты по шагам. Полное сообщение восстанавливается только после обработки всей последовательности токенов.
9. Для KL и TVD RRC предоставляет явный `Q_stego`. Оно независимо строится как мера токенных подинтервалов после того же численного разбиения текущего `P_reference`; сертификат `Q=P` не используется.
10. Построение полного `Q_stego` относится к измерительному контуру и не входит во время работы RRC согласно ADR-0020.

## Следствия

- нормализованный RRC не владеет языковой моделью, токенизатором или общей политикой генерации;
- `top-k` не дублируется внутри метода и поэтому не возникает скрытого второго распределения после `P_reference`;
- основной режим остановки RRC — `fixed_payload_bits` с обязательным защитным пределом числа токенов;
- алгоритмическую корректность необходимо оценивать отдельно на исходных token IDs и после текстового канала, поскольку повторная токенизация может изменить последовательность токенов;
- оба направления KL и TVD рассчитываются общим модулем бенчмарка по явному `Q_stego`.
