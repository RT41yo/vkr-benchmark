# Закрытие Этапа 2: базовая экспериментальная инфраструктура

Статус: **Этап 2 технически готов и имеет полный комплект предусмотренных ROADMAP результатов**. Автоматическая проверка завершилась сообщением `Stage 2 technical readiness: READY`.

Этот документ сопоставляет выполненные работы и полученные результаты с ROADMAP.

## 1. Выполненные работы

### 1.1. Bins, Huffman и Arithmetic Coding подключены к единой инфраструктуре

Все три базовых метода используют общий интерфейс кодирования и декодирования, общий адаптер языковой модели, каноническое `P_reference`, раздельные источники случайности и единый текстовый канал передачи.

При проверке восстановления декодеру передаётся только обычный текст. Исходные идентификаторы токенов отправителя напрямую не используются.

Ключевые файлы реализации:

- `src/vkr_benchmark/methods/bins.py`;
- `src/vkr_benchmark/methods/huffman.py`;
- `src/vkr_benchmark/methods/arithmetic.py`;
- `src/vkr_benchmark/runner/streaming.py`;
- `src/vkr_benchmark/runner/experiment.py`.

### 1.2. Реализован единый порядок проведения эксперимента

Один и тот же модуль запуска задаёт:

- промпт по `prompt_id`;
- секретную последовательность по `secret_id`;
- параметры метода;
- общую политику генерации;
- заданную длину генерируемого фрагмента.

В едином контуре рассчитываются:

- полезная нагрузка и BPT;
- энтропия `P_reference` и эффективность её использования;
- `D_KL(P_reference || Q_stego)` и TVD;
- NLL и PPL исходной языковой модели;
- надёжность восстановления и BER;
- время встраивания и извлечения, а также его разложение на общие и специфичные для метода операции.

Точные определения и правила расчёта приведены в `docs/reference/metrics.md`.

### 1.3. Реализован единый формат хранения запусков

Каждая каноническая конфигурация получает `run_id = SHA256(canonical_config_json)[:16]`.

Для успешного запуска сохраняются:

- `config.json`;
- `result.json`;
- `stegotext.txt`;
- `token_ids.json`;
- `trace.jsonl.gz`.

Общая таблица находится в `results/summary.parquet`. Повторный запуск той же конфигурации обновляет запись по `run_id`, не создавая логический дубликат.

## 3. Автоматическая проверка готовности

Для итоговой проверки используется:

```bash
python scripts/check_stage2_readiness.py --run-tests \
  --json-output results/stage2_readiness.json
```

Проверяются:

- наличие ключевых файлов реализации, конфигурации и документации;
- читаемость `results/summary.parquet`;
- успешный статус Bins, Huffman и Arithmetic Coding;
- уникальность `run_id`;
- `BER = 0`;
- точное восстановление полезной нагрузки;
- корректность текстового канала;
- допустимые диапазоны базовых метрик;
- `q_mode = analytic_exact` для трёх базовых методов;
- отсутствие секретных токенов Hugging Face среди отслеживаемых файлов;
- успешное прохождение полного набора тестов при использовании `--run-tests`.

Значение `+inf` для `D_KL(P_reference || Q_stego)` не считается ошибкой: при потере части области поддержки это корректный математический результат.

Фактический результат проверки:

`Stage 2 technical readiness: READY`.

## 4. Ограничения результатов Этапа 2

Численные значения проверочного запуска нельзя трактовать как итоговое ранжирование методов. Они получены для одной модели, одного технического промпта, одной секретной последовательности, одной точки параметров каждого метода и 16 токенов-носителей.

Временные показатели не усреднены по повторным запускам. Промпт `p000001` не является окончательным корпусом бенчмарка.

Диапазоны параметров методов, число промптов, секретов и повторов, а также окончательная спецификация v1.0 относятся к последующим этапам ROADMAP.

## 5. Переход к Этапу 3

На Этапе 3 необходимо проверить воспроизводимость Bins, Huffman и Arithmetic Coding относительно исходных публикаций и авторских реализаций.

Следует чётко разделять два режима:

- `normalized` — единые условия нашего бенчмарка;
- `author-compatible` — условия, необходимые для воспроизведения конкретного авторского результата.

Для проверки сходимости к авторским работам будут рассчитываться оба направления KL:

- `D_KL(P_reference || Q_stego)` — базовое направление бенчмарка;
- `D_KL(Q_stego || P_reference)` — дополнительное направление для сопоставления с работами, где используется именно оно.

Для каждого воспроизводимого результата необходимо фиксировать направление KL, единицы измерения, способ агрегирования и точные настройки исходной реализации.
