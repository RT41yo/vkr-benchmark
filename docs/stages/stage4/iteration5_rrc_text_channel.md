# Этап 4 — итерация 5: серийная проверка надежности RRC

**Дата:** 2026-10-09  
**Метод:** Rotation Range-Coding (RRC)  
**Авторская версия:** `ryehr/RRC_steganography@dae326259e4fca8bc4fcf460dafdbc0e88a0a71a`

## Состояние перед серийной проверкой

Нормализованный RRC прошел прямое сравнение с неизмененным авторским `rrc_core.py`: 68 фикстур, 0 расхождений, статус PASS. Отдельная полнословарная проверка явного `Q_stego` на Llama-3.2-3B также прошла: 25 шагов, 0 отказов, оба направления KL порядка `10^-16`, максимальный TVD `2.85e-12`. Это соответствует только накопленной численной погрешности при работе с поддержкой примерно 128 тыс. токенов.

Следующая проверка отделяет надежность самого RRC от надежности обычного текстового транспорта.

## Что измеряется

Для 100 детерминированных секретов по 128 бит используется один зафиксированный benchmark prompt `p000001`, одна модель, один ключ `42` и одна generation policy. Для каждого секрета выполняются две независимые проверки декодирования.

Первая получает непосредственно token IDs отправителя. Она изолирует алгоритм RRC и является строгим gate: все сообщения должны восстановиться точно.

Вторая передает носитель только как обычный текст: `token IDs → decode text → retokenize → token IDs`. Здесь отдельно измеряются точность повторной токенизации и точность восстановления секрета. Эти показатели не обязаны быть 100%, потому что возможное изменение сегментации при повторной токенизации является свойством текстового канала, а не арифметики RRC.

Статус PASS не скрывает ошибки текстового канала. Он означает только, что нет ошибок кодирования, direct token-ID recovery равен 100%, а при неизменной последовательности токенов текстовый путь не дает другого секрета.

## Зафиксированная конфигурация

Конфигурация находится в `configs/reproducibility/stage4_rrc_text_channel.json`:

- 100 секретов;
- 128 бит на секрет;
- максимум 256 carrier tokens;
- `precision_margin = 40`;
- `verify_termination = true`;
- `key = 42`;
- полный `P_reference`, без внутреннего top-k RRC;
- секреты `stage4-rrc-text-000001` ... `stage4-rrc-text-000100`.

Результат сохраняется в `results/stage4/rrc/text_channel_llama.json`. В JSON сохраняются агрегаты и только проблемные/изменившиеся примеры, чтобы можно было отдельно анализировать случаи ретокенизации.
