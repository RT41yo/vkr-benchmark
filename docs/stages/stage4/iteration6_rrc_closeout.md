# Этап 4 — итерация 6: закрытие RRC

**Дата:** 2026-10-09  
**Метод:** Rotation Range-Coding (RRC)  
**Авторская версия:** `ryehr/RRC_steganography@dae326259e4fca8bc4fcf460dafdbc0e88a0a71a`

## Итоговый статус

RRC закрыт как отдельный метод Этапа 4.

Подтверждено:

- normalized fixed-payload lifecycle;
- точное прямое восстановление 128-битных сообщений;
- прямое соответствие неизмененному авторскому `rrc_core.py`: 68/68 фикстур;
- независимый полнословарный `Q_stego` без сертификата `Q=P`;
- на 25 реальных Llama distributions: оба KL порядка `10^-16`, max TVD `2.85e-12`, 0 отказов;
- 100/100 direct token-ID round-trips в серийной проверке;
- 98/100 ordinary-text round-trips; оба отказа совпали с изменением token sequence при повторной токенизации;
- verified termination реально потребовал продолжения генерации: 3 retries суммарно, максимум 2 на сообщение;
- стоимость metric instrumentation отделена от performance метода.

Характерный unified-run для 128 бит завершился за 25 carrier tokens, дал 5.12 bit/token и 99.277% использования энтропии при BER=0.

## Интерпретация text-channel результата

Статус RRC не понижается из-за 98/100 ordinary-text recovery: строгая алгоритмическая проверка по исходным token IDs дала 100/100. В двух проблемных случаях изменились token IDs после преобразования `token IDs → text → token IDs`; случаев `token-exact but secret wrong` не было.

Поэтому эти два отказа относятся к transport/tokenization layer и должны храниться как отдельная характеристика, а не смешиваться с корректностью RRC.
