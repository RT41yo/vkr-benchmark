# Протокол проверки воспроизводимости RRC

## Цель

Проверить, что нормализованная реализация Rotation Range-Coding сохраняет ключевые свойства авторского метода и корректно работает в общей инфраструктуре бенчмарка.

Основной источник для Этапа 4 — `ryehr/RRC_steganography`, коммит `dae326259e4fca8bc4fcf460dafdbc0e88a0a71a`. Ранний анализ по `8b6a86a...` сохраняется только как история происхождения предварительных выводов.

## Границы адаптации

RRC получает готовое `P_reference`. Общие `temperature`, `top-k` и `top-p` применяются до вызова метода. Поэтому параметр `top-k` из авторских запусков при необходимости воспроизводится через общую политику генерации, а не повторяется внутри RRC.

Метод работает с сообщением фиксированной длины. Число токенов определяется самим range coding и ограничивается только защитным пределом. Отправитель и получатель используют один ключ для воспроизведения последовательности псевдослучайных вращений.

Точность вычислений зависит от длины сообщения и рассчитывается по правилу актуальной авторской реализации. Перед завершением кодирования выполняется дополнительная проверка обратным воспроизведением извлечения.

## Проверки

Проверка включает четыре части:

1. синтетические тесты арифметики интервалов, вращения, завершения и обратного восстановления сообщения;
2. точное восстановление секрета по исходной последовательности token IDs;
3. отдельную оценку восстановления после преобразования `token IDs → text → token IDs`;
4. расчет явного `Q_stego` и обоих направлений KL вместе с TVD общим модулем метрик.

Для `Q_stego` не используется заранее заданное равенство `Q=P`. Распределение строится независимо по длинам токенных подинтервалов, которые определяют вероятность выбора токена при равномерном вращении точки внутри текущего диапазона.

## Характерный результат

На этапе проверки воспроизводимости необходимо подтвердить характерное для RRC сочетание высокой утилизации энтропии и практически нулевого распределительного искажения. Точное совпадение скорости и чисел публикации не требуется, поскольку в нормализованном режиме используются выбранные для ВКР модели и единая инфраструктура бенчмарка.

Отдельно фиксируется разница между надежностью на исходных token IDs и после текстового канала. Ошибка повторной токенизации считается наблюдаемым свойством канала и не исправляется скрытым восстановлением токенов.

## Уровни подтверждения соответствия

Чтобы не смешивать разные виды доказательств, для RRC используются три отдельных проверки.

**Source-oracle.** Нормализованный адаптер сравнивается с независимой Python-транскрипцией арифметики зафиксированного `rrc_core.py` на синтетических `P_reference`. Сравниваются последовательность token IDs, восстановленный секрет, число цифр `Decimal` и verified-termination retries. Эта проверка входит в обычный тестовый контур, но сама по себе не означает, что был выполнен оригинальный авторский файл.

**Прямой авторский запуск.** `scripts/run_stage4_rrc_author_conformance.py` импортирует оригинальный `rrc_core.py` из чистого checkout `external/RRC_steganography`, проверяет точный HEAD `dae326259...` и отсутствие локальных изменений. Fake LM stepper передает авторскому ядру те же уже готовые `P_reference`, поэтому сравнение не зависит от другой языковой модели или внутреннего author top-k.

**Явный Q.** `scripts/check_stage4_rrc_explicit_q.py` независимо строит полный `Q_stego` как вектор относительных длин токенных интервалов и затем использует общие benchmark-функции для `KL(P||Q)`, `KL(Q||P)` и TVD. Проверка выполняется сначала на синтетических распределениях, затем на реальных `P_reference` выбранной Llama. Сертификат равенства `Q=P` не используется.

## Граница интерпретации Q_stego

Построение `Q_stego` основано на механизме RRC: перед выбором токена фиксированная секретная точка сдвигается свежим равномерным вращением по текущему диапазону. Поэтому вероятность попадания в токенный подинтервал равна относительной длине этого подинтервала. В benchmark это свойство не подставляется как готовый ноль KL: из границ интервалов строится явный массив вероятностей, который затем сравнивается с `P_reference`.

Как и для Discop, стоимость построения полного `Q_stego` относится только к измерительному контуру. Она не участвует в выборе токена и исключается из показателей скорости RRC.

## Численная интерпретация полнословарного Q_stego

Для маленьких синтетических распределений проверяется почти побитовое совпадение `Q_stego` с нормализованным `P_reference`. Для реальной Llama с поддержкой порядка `10^5` токенов это требование некорректно: RRC строит отсортированные кумулятивные границы последовательным FP64-накоплением, а общий metric layer независимо нормализует канонический FP32 `P_reference`. Эти математически эквивалентные операции дают небольшой накопленный численный остаток.

Поэтому на реальной траектории критерием являются конечность обоих KL, `KL <= 1e-12` бит/токен и `TVD <= 1e-9`. `max |Q-P|` сохраняется как диагностический показатель, но не используется как самостоятельный gate. Это решение зафиксировано в ADR-0022. Никакого сертификата `Q=P` или подгонки `Q` под `P_reference` не применяется.


## Серийная проверка текстового канала

После успешного source-oracle, прямого author conformance и explicit-Q запускается серия из 100 фиксированных 128-битных секретов на benchmark prompt `p000001`. Для каждого сообщения отдельно считаются direct token-ID recovery и ordinary-text recovery после `token IDs → text → retokenization`.

Direct token-ID recovery должен быть 100% и является проверкой самого RRC. Доля точной повторной токенизации и доля восстановления секрета через текстовый канал являются измеряемыми характеристиками транспорта и не подменяются скрытым восстановлением исходных token IDs. Поэтому изменение токенизации само по себе не переводит conformance RRC в FAIL. Отдельно запрещен более опасный случай: если token IDs после текстового канала совпали с исходными, а секрет не восстановился, это считается алгоритмическим отказом.

## Зафиксированные результаты серийной проверки

На Llama-3.2-3B серия из 100 сообщений завершилась со следующими результатами: direct token-ID recovery `100/100`, точная повторная токенизация `98/100`, text-channel secret recovery `98/100`. Случаев `token-exact but secret wrong` и `token-changed but secret recovered` не было. Число carrier tokens составило от 16 до 83, среднее 36.250; средний BPT по сообщениям — 3.826830. Verified termination потребовал 3 дополнительных продолжения генерации, максимум 2 для одного сообщения.

Таким образом, два текстовых отказа локализованы в transport/tokenization layer: они совпали с двумя случаями изменения token sequence после повторной токенизации. Алгоритмический direct-ID gate пройден полностью.
