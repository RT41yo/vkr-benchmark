# Этап 4 — отчет о воспроизводимости RRC

**Дата фиксации:** 2026-10-09  
**Метод:** Rotation Range-Coding (RRC)  
**Авторская реализация:** `ryehr/RRC_steganography@dae326259e4fca8bc4fcf460dafdbc0e88a0a71a`  
**Модель в бенчмарке:** `meta-llama/Llama-3.2-3B@13afe5124825b4f3751f836b40dafda64c1ed062`

## Цель проверки

Проверка должна была подтвердить, что нормализованная реализация RRC воспроизводит актуальную авторскую арифметику range coding и rotation, обеспечивает точное восстановление сообщения, сохраняет распределение `P_reference` и корректно работает в общей инфраструктуре бенчмарка.

Прямое совпадение чисел публикации не ставилось целью: в бенчмарке используется выбранная для ВКР Llama-3.2-3B и единый контур построения `P_reference`. Для RRC отдельно различаются надежность самого алгоритма по исходным token IDs и надежность обычного текстового канала после повторной токенизации.

## Какой результат публикации воспроизводится

Для RRC также разделяются два независимых уровня.

**Соответствие реализации.** Прямая проверка с зафиксированным `rrc_core.py` подтверждает, что нормализованный адаптер воспроизводит авторскую арифметику интервалов, rotation, precision и verified termination на одинаковых входах.

**Характерный результат публикации.** На уровне научного результата проверяется заявленное для RRC сочетание практически полного сохранения исходного распределения и почти полного использования энтропии при корректном извлечении. В бенчмарке это проверяется через независимый полный `Q_stego`, расчет обоих направлений KL и TVD, эффективность использования энтропии в запуске с фиксированной полезной нагрузкой и прямое восстановление по token IDs.

Таким образом, авторский репозиторий не используется вместо статьи. Он служит эталоном программной семантики, тогда как метрики распределения, емкости и надежности проверяют характерное поведение, ради которого метод предложен в публикации. Такой двухуровневый подход зафиксирован в ADR-0023.

## Нормализованная семантика

RRC получает уже готовое `P_reference`. Общие `temperature`, `top-k` и `top-p` применяются до метода. Внутреннего `top-k` в normalized RRC нет.

Сообщение имеет фиксированную длину, а число carrier tokens определяется самим range coding. Отправитель и получатель используют один ключ для воспроизведения последовательности вращений. Рабочая точность `Decimal` выводится из длины сообщения с дополнительным запасом. Перед остановкой encoder выполняет обратное воспроизведение extraction и продолжает генерацию, если простое условие завершения еще не гарантирует точное восстановление секрета.

## Характерный запуск на Llama-3.2-3B

Для фиксированного сообщения длиной 128 бит RRC завершил кодирование за 25 токенов.

| Показатель | Значение |
|---|---:|
| Payload | 128 бит |
| Carrier tokens | 25 |
| BPT | 5.120 |
| Средняя энтропия `P_reference` | 5.157299 бит/токен |
| Суммарная энтропия | 128.932476 бит |
| Использование энтропии | 99.277% |
| BER | 0 |
| Token-ID round-trip | точный |
| Text round-trip | точный |
| Encode | 49.599 ms/token |
| Decode | 49.141 ms/token |

В этом запуске 128 полезных бит были размещены при доступной суммарной энтропии около 128.93 бит, то есть потери относительно энтропийного предела составили менее одного бита на все сообщение.

## Прямое соответствие авторскому ядру

Нормализованный адаптер был сравнен непосредственно с неизмененным авторским `rrc_core.py` из зафиксированного коммита. Обоим вариантам подавались одинаковые синтетические `P_reference`, одинаковые секреты и одинаковый ключ; языковая модель в этой проверке не участвовала.

Результат:

- 68 фикстур;
- 0 расхождений;
- авторский checkout после запуска остался неизмененным;
- статус `PASS`.

Таким образом, normalized RRC воспроизводит зафиксированное авторское алгоритмическое ядро на проверяемых траекториях, включая выбор token IDs, обратное восстановление сообщения, рабочую точность и verified termination.

## Независимый расчет `Q_stego`

Для RRC не используется сертификат `Q=P`. Полный массив `Q_stego` независимо строится из относительных длин токенных подинтервалов, после чего оба направления KL-дивергенции и TVD считаются общим модулем метрик бенчмарка.

На 131 небольшом синтетическом распределении получено:

- 0 отказов;
- max `|Q-P| = 1.11e-16`;
- max KL `P→Q = 1.38e-16` бит/токен;
- max KL `Q→P = 3.73e-16` бит/токен;
- max TVD `= 1.12e-15`.

Дополнительный stress-test на поддержке 128256 токенов также прошел. Он показал, что при полнословарном FP64-накоплении TVD естественно может находиться на уровне `10^-12`, даже когда KL остается около машинной точности.

На 25 реальных последовательных `P_reference` Llama-3.2-3B:

- 0 отказов;
- размер ненулевой поддержки на каждом шаге: 128254 токена;
- max `|Q-P| = 1.15e-13`;
- max KL `P→Q = 4.76e-16` бит/токен;
- max KL `Q→P = 5.85e-16` бит/токен;
- max TVD `= 2.85e-12`;
- статус `PASS`.

Оба направления KL конечны и находятся на уровне численной погрешности. Небольшой полнословарный остаток TVD объясняется различием порядка FP64-накопления границ и независимой нормализацией канонического FP32 `P_reference`; никакого сглаживания, подстановки `Q=P` или изменения support не применяется.

## Серийная надежность текстового канала

Проведена серия из 100 детерминированных 128-битных сообщений на prompt `p000001`, ключе `42`, `precision_margin = 40` и максимальном бюджете 256 carrier tokens.

Результат:

| Проверка | Результат |
|---|---:|
| Direct token-ID recovery | 100/100 (100%) |
| Точная повторная токенизация текста | 98/100 (98%) |
| Восстановление секрета через текстовый канал | 98/100 (98%) |
| Token IDs совпали, но секрет неверен | 0 |
| Token IDs изменились, но секрет восстановился | 0 |
| Carrier tokens, min / mean / max | 16 / 36.250 / 83 |
| Средний BPT по сообщениям | 3.826830 |
| Verified-termination retries, sum / max | 3 / 2 |

Все 100 сообщений точно восстановились, когда receiver получал исходные token IDs sender. Два отказа текстового пути в точности совпали с двумя случаями изменения token sequence после `decode → text → retokenize`. Случаев, когда token IDs сохранились, но RRC восстановил неправильный секрет, не было.

Следовательно, в этой серии алгоритмическая надежность RRC составила 100%, а наблюдаемые 2% отказов ordinary-text transport связаны с неоднозначностью повторной токенизации, а не с range coding или rotation.

Verified termination реально сработал в эксперименте: суммарно потребовалось три дополнительных продолжения генерации, максимум два для одного сообщения. Это подтверждает, что защитная проверка не является недостижимой ветвью и участвует в реальных траекториях.

Средний BPT в таблице — среднее индивидуальных значений `128 / n_tokens` по 100 сообщениям. Поэтому он не обязан совпадать с `128 / mean(n_tokens)`.

## Производительность и измерительный контур

Построение полного `Q_stego`, KL/TVD, энтропия и другие исследовательские метрики относятся к измерительному контуру и не включаются в показатели скорости RRC. В характерном запуске metric instrumentation составила 102.313 ms сверх алгоритмического времени.

Это позволяет сравнивать скорость самого метода, не штрафуя RRC за дополнительные проверки, необходимые только бенчмарку.

## Ограничения текущей проверки

Серийная text-channel проверка выполнена на одном benchmark prompt и одной модели. Полученные 98% не следует интерпретировать как универсальную надежность текстового транспорта RRC. Более широкое сравнение по prompts, моделям и рабочим точкам относится к последующим этапам экспериментов.

Аналогично, характерный запуск с 99.277% использования энтропии является иллюстрацией ожидаемого поведения, а не оценкой среднего качества метода по корпусу.

## Вывод

RRC успешно прошел интеграционную и воспроизводимостную проверку Этапа 4. Нормализованная реализация совпала с зафиксированным авторским ядром на 68 фикстурах, обеспечила 100/100 точных восстановлений по исходным token IDs в серийной проверке и независимо подтвердила практически нулевое распределительное искажение на реальных `P_reference` Llama-3.2-3B.

В обычном текстовом канале восстановлено 98/100 сообщений; оба отказа объясняются изменением токенизации. Поэтому алгоритмическую часть RRC следует считать воспроизведенной, а надежность текстового транспорта — отдельной измеряемой характеристикой.
