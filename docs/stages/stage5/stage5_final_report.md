# Этап 5 — итоговый отчёт по пилотным экспериментам

## 1. Цель этапа

На Этапе 5 нужно было подготовить основные эксперименты так, чтобы на Этапе 6 уже не подбирать параметры, а запускать заранее зафиксированный протокол.

Для этого требовалось:

- выбрать общие условия генерации;
- проверить широкий набор параметров методов;
- оставить содержательные рабочие точки;
- разобраться с ошибками восстановления секрета;
- отдельно откалибровать RRC;
- определить число промптов и повторов для основных экспериментов;
- оценить вычислительный бюджет;
- подготовить окончательную спецификацию бенчмарка v1.0.

Данные задачи выполнены.

## 2. Общий режим генерации

Для всех нормализованных сравнений зафиксирован один общий режим:

```text
temperature = 1.0
top_k = null
top_p = 1.0
exclude_special_tokens = true
kv_cache = true
```

На предварительной проверке `top_p=0.98` оказался несовместим с частью конфигураций Bins: после общего ограничения распределения в некоторых корзинах не оставалось допустимых токенов. Поэтому для основного бенчмарка используется `top_p=1.0`.

Такое решение позволяет сравнивать методы на одном и том же полном `P_reference`, не обрезая его общей top-p фильтрацией.

Подробности: `docs/stages/stage5/top_p_calibration_report.md`.

## 3. Pilot A — широкий отбор параметров

Pilot A был первым широким перебором параметров шести потоковых методов.

Условия:

```text
модель: Llama-3.2-3B
4 промпта
2 повтора
128 токенов-носителей
45 рабочих точек
360 запусков
```

Проверялись разные значения параметров Bins, Huffman, Arithmetic Coding и DAIRstega. ADG и Discop проверялись в одной нормализованной конфигурации.

Из 360 запусков:

```text
347 завершились без программной ошибки
318 дали точное восстановление после передачи через текст
42 результата были неточными
```

Дополнительная диагностика показала, что эти 42 случая связаны с изменением последовательности токенов после цепочки:

```text
token IDs → text → retokenization
```

После Pilot A из 45 точек были оставлены 21 точка для более строгой проверки в Pilot B. Остальные точки либо дублировали соседние режимы, либо были малоинтересны для основного сравнения.

Основные документы:

- `docs/stages/stage5/pilot_a_analysis.md`;
- `docs/stages/stage5/pilot_a_reliability_analysis.md`;
- `docs/stages/stage5/pilot_b_operating_point_selection.md`.

## 4. Pilot B — подтверждение выбранных режимов

Pilot B использовал более длинную генерацию и больше повторов:

```text
модель: Llama-3.2-3B
8 промптов
3 повтора
256 токенов-носителей
21 рабочая точка
504 запуска
```

Получено:

```text
404 точных полных цикла
62 запуска завершились, но секрет восстановился неточно
38 запусков завершились ошибкой при декодировании
```

Таким образом, 100 из 504 результатов не дали точного восстановления по полному текстовому пути.

На этом этапе нельзя было просто считать, что проблема снова связана с повторной токенизацией. Поэтому был проведён отдельный аудит декодеров.

## 5. Аудит декодеров

Аудит проверял, действительно ли ошибки Pilot B вызваны декодерами или возникают раньше — при передаче через текст.

Получены четыре основных результата.

### 5.1. Прямое декодирование токенов отправителя

Для всех 504 конфигураций декодирование токенов отправителя было точным:

```text
504 / 504 exact
```

Для 38 исходных жёстких ошибок токены отправителя пришлось детерминированно восстановить, потому что в старом формате неудачного запуска они не сохранялись. Это ограничение явно зафиксировано в отчёте.

### 5.2. Независимая проверка декодеров

Декодеры шести методов были проверены независимой логикой:

```text
3533 проверки
0 расхождений
6 / 6 методов прошли проверку
```

### 5.3. 62 неточных результата после успешного завершения

Во всех 62 случаях:

- токены отправителя декодировались точно;
- после преобразования в текст и повторной токенизации последовательность токенов менялась;
- неточный результат возникал уже на изменённой последовательности.

Итого:

```text
62 / 62 связаны с текстовым каналом
```

### 5.4. 38 жёстких ошибок

Все 38 исходных ошибок были повторно воспроизведены после текстового канала на детерминированно восстановленных токенах отправителя. Тип и текст исходной ошибки совпали.

Итого:

```text
38 / 38 воспроизведены после text → retokenization
```

Аудит не выявил дефектов декодеров.

При этом результаты Pilot B не пересчитываются в `504/504`. Для бенчмарка нормативным остаётся полный путь через обычный текст, поэтому фактическая надёжность по-прежнему оценивается по результату после повторной токенизации.

Полный отчёт: `docs/stages/stage5/decoder_audit_report.md`.

## 6. Финальные рабочие точки шести потоковых методов

После Pilot B оставлены 14 рабочих точек.

### Bins

```text
b1: block_size = 1
b4: block_size = 4
b6: block_size = 6
```

Три точки показывают переход от низкой ёмкости к высокой. Рост ёмкости сопровождается сильным ухудшением качества текста и высокой чувствительностью полного текстового канала.

### Huffman

```text
e2: bits_per_word = 2
e4: bits_per_word = 4
e8: bits_per_word = 8
```

Сохраняются низкий, промежуточный и максимальный проверенный режимы. Точка `e6` исключена как промежуточная и мало добавляющая к сравнению `e4` и `e8`.

### Arithmetic Coding

```text
p32-k128:   precision = 32, top_k = 128
p32-k2048:  precision = 32, top_k = 2048
p32-k50000: precision = 32, top_k = 50000
```

Для основных экспериментов фиксируется `precision=32`. Значения `16` и `48` использовались как проверка влияния точности, но не нужны как отдельные основные точки.

Три выбранных значения `top_k` показывают переход от заметного ограничения множества кандидатов к почти полному распределению.

### ADG

```text
default
```

ADG не имеет отдельной сетки управляющих параметров в нормализованной реализации, поэтому используется одна точка.

### Discop

```text
default
```

Для Discop также используется одна нормализованная точка.

### DAIRstega

```text
a8-b1-k100:     alpha = 8,  beta = 1.0,  top_k = 100
a16-b075-k100:  alpha = 16, beta = 0.75, top_k = 100
a32-b05-k100:   alpha = 32, beta = 0.5,  top_k = 100
```

Эти три точки оставлены как разные режимы компромисса между ёмкостью и качеством. Последняя точка специально сохраняется как крайний режим высокой ёмкости, хотя её качество и надёжность хуже.

Полное обоснование: `docs/stages/stage5/pilot_b_stage6_operating_point_selection.md`.

## 7. RRC

RRC исследовался отдельно, потому что у него другая схема работы. Потоковые методы получают фиксированные 256 токенов и используют столько секретных битов, сколько успевают встроить. RRC получает сообщение фиксированной длины и сам определяет, сколько токенов потребуется.

### 7.1. Проверка численной точности

Сначала проверялись:

```text
precision_margin = 20, 40, 60
payload = 1024 bits
```

Все 24 запуска восстановили секрет точно. Однако в части запусков `forward KL` становилась `+inf`, хотя TVD была практически нулевой.

Отдельная диагностика показала точную причину: очень маленькие положительные вероятности исчезали при последовательном накоплении границ в FP64. Из-за этого для некоторых токенов получалось:

```text
P_reference > 0
Q_stego = 0
```

После переноса построения границ в `Decimal` проблема исчезла.

Проверка исправленного варианта дала:

```text
8 / 8 запусков завершились
8 / 8 имеют конечные обе KL
max forward KL ≈ 1.38e-16 бит
max TVD ≈ 1.03e-16
```

Один из восьми полных текстовых циклов восстановил секрет неточно. Для него было отдельно проверено декодирование сохранённых токенов отправителя:

```text
1024 / 1024 бит восстановлены точно
BER = 0
```

После повторной токенизации число токенов изменилось с 249 до 250. Следовательно, этот случай связан с текстовым каналом, а не с численной реализацией RRC.

### 7.2. Выбор длины секрета

Проверены четыре размера:

```text
128, 256, 512, 1024 бит
```

Всего выполнено 32 запуска.

Для Stage 6 выбран:

```text
payload_bits = 1024
precision_margin = 40
verify_termination = true
```

Главная причина выбора — сопоставимый масштаб текста. Для 1024 бит медианная длина равна 256 токенам, средняя — 253 токена. Это почти совпадает с 256 токенами у потоковых методов.

Медианная скорость встраивания составляет примерно 4 бита на токен. Обе KL и TVD после исправления границ остаются на уровне численной погрешности.

Основные документы:

- `docs/stages/stage5/rrc_decimal_boundary_validation_report.md`;
- `docs/stages/stage5/rrc_payload_calibration_report.md`.

## 8. Итоговый набор режимов для Stage 6

В основных экспериментах используются семь методов и 15 режимов:

| Метод | Рабочие точки |
|---|---|
| Bins | `b1`, `b4`, `b6` |
| Huffman | `e2`, `e4`, `e8` |
| Arithmetic Coding | `p32-k128`, `p32-k2048`, `p32-k50000` |
| ADG | `default` |
| Discop | `default` |
| DAIRstega | `a8-b1-k100`, `a16-b075-k100`, `a32-b05-k100` |
| RRC | `payload_bits=1024`, `precision_margin=40` |

Первые шесть методов работают в режиме фиксированных 256 токенов. RRC работает отдельно в режиме фиксированных 1024 бит секрета.

## 9. Масштаб основных экспериментов

Stage 6 использует 24 новых промпта, которые не участвовали в Pilot A и Pilot B.

Источник остаётся тем же — CNN/DailyMail. В Stage 5 использовались записи с `selection_rank=0..7`, а для Stage 6 зафиксированы следующие 24 записи:

```text
selection_rank = 8..31
prompt_id = s6p0001..s6p0024
```

Это отделяет подбор параметров от основной оценки.

### Llama-3.2-3B

```text
24 промпта
3 повтора
14 потоковых точек + RRC
1080 запусков
```

### Qwen3-4B-Base

```text
те же 24 промпта
2 повтора
те же 14 потоковых точек + RRC
720 запусков
```

Всего:

```text
1800 стегозапусков
```

Контрольные тексты для стегоанализа в это число не входят. Они формируются отдельно на Этапе 7.

## 10. Вычислительный бюджет

По фактическому времени Pilot B и калибровки RRC один полный набор из 15 режимов для одного сочетания `prompt × replicate` занимает примерно 26 минут на Llama.

Полученная оценка:

| Оценка | Llama | Qwen | Всего |
|---|---:|---:|---:|
| По медианным временам | 31.6 ч | 29.5 ч | 61.1 ч |
| Консервативная | 36.5 ч | 34.1 ч | 70.6 ч |

С резервом 20% верхний ориентир составляет около:

```text
85 часов последовательного GPU-времени
```

Это примерно 3.5 суток непрерывного выполнения на одной GPU.

Подробности: `docs/stages/stage5/stage6_scale_and_budget_report.md`.

## 11. Что зафиксировано для Stage 6

После Этапа 5 больше не требуется подбирать параметры методов.

Зафиксированы:

- семь методов;
- 14 потоковых рабочих точек;
- отдельный режим RRC;
- общий режим формирования `P_reference`;
- 256 токенов для потоковых методов;
- 1024 бита для RRC;
- 24 новых промпта;
- три повтора на Llama;
- два повтора на Qwen;
- одинаковые первые два `secret_id` для обеих моделей;
- обе стороны KL, TVD, BPT, использование энтропии, NLL/PPL, надёжность и время;
- полный текстовый путь `token IDs → text → retokenization → decode` как нормативная проверка надёжности.

Исполняемые конфигурации Stage 6 находятся в:

```text
configs/experiments/stage6_main_streaming_llama.json
configs/experiments/stage6_main_rrc_llama.json
configs/experiments/stage6_main_streaming_qwen.json
configs/experiments/stage6_main_rrc_qwen.json
```

Окончательные правила эксперимента собраны в:

`specification/benchmark_specification_v1.0.md`.

## 12. Итог Этапа 5

Этап 5 выполнил свою основную задачу: пилотные эксперименты превратили широкий набор возможных параметров в конкретный и воспроизводимый план основных сравнений.

Главные результаты этапа:

1. общий режим генерации выбран и проверен;
2. широкий набор параметров сокращён до содержательных рабочих точек;
3. причина ошибок Pilot B исследована отдельно и не связана с дефектами декодеров;
4. у RRC найден и устранён численный артефакт FP64;
5. для RRC выбран режим, сопоставимый по длине текста с потоковыми методами;
6. для Stage 6 выбраны новые промпты и число повторов;
7. рассчитан вычислительный бюджет;
8. подготовлена спецификация бенчмарка v1.0 и исполняемые конфигурации основных экспериментов.
