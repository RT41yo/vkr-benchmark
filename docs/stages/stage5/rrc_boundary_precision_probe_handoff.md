# RRC: диагностика точности границ интервалов

## Цель

У RRC после калибровки `precision_margin` остаётся отдельный численный вопрос.
В части запусков наблюдается сочетание:

```text
forward KL = +inf
reverse KL ≈ 0
TVD ≈ 1e-12
```

При этом секрет восстанавливается точно, а изменение `precision_margin` от 20 до 60 не меняет результат.

Задача этой диагностики — проверить рабочую гипотезу: очень маленькая положительная вероятность из `P_reference` теряется при построении накопительных границ в FP64, поэтому соответствующий интервал RRC получает нулевую ширину.

## Что проверяется

Диагностика не меняет RRC и не предлагает новую реализацию.

Для каждой выбранной конфигурации она:

1. повторяет запуск RRC с текущей реализацией;
2. получает исходную последовательность токенов отправителя;
3. повторно проходит по этой последовательности через ту же языковую модель;
4. на каждом шаге заново строит `P_reference`;
5. проверяет FP64-границы RRC;
6. находит случаи, где одновременно выполняется:

```text
P_reference(token) > 0
Q_RRC(token) = 0
```

7. считает суммарную потерянную вероятность;
8. проверяет, совпадают ли такие шаги со шагами, на которых `forward KL = +inf`.

## Почему используется только `margin40`

Калибровка уже показала, что для одного и того же промпта и повтора траектория RRC при `precision_margin = 20`, `40` и `60` одинакова.

Поэтому повторять все 24 запуска не нужно. Для диагностики достаточно восьми запусков `margin40`:

```text
4 промпта × 2 повтора = 8 запусков
```

Это отделяет вопрос Decimal-точности диапазона от вопроса FP64-точности границ вероятностных интервалов.

## Критерий подтверждения причины

Рабочая гипотеза считается подтверждённой на проверенной выборке, если:

- каждый шаг с `forward KL = +inf` содержит хотя бы один положительный токен с нулевой шириной FP64-интервала;
- шагов с такой потерей поддержки без соответствующего `forward KL = +inf` нет;
- повторный расчёт метрики на тех же FP64-границах совпадает с исходной классификацией;
- при сохранении исходной положительной поддержки проблема `+inf` исчезает.

Последний пункт используется только как численная контрольная проверка. Он не означает автоматического изменения production RRC.

## Что будет после диагностики

Если причина подтверждается, отдельно принимается решение о Stage 6:

1. либо сохранить текущую реализацию RRC и честно учитывать конечную точность как свойство практической реализации;
2. либо согласовать изменение способа построения границ и после этого повторить небольшую калибровку RRC.

До получения результата этой диагностики production-код RRC не меняется.
