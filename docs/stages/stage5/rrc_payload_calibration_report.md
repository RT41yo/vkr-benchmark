# Stage 5 — итог калибровки размера секрета RRC

## 1. Цель

После исправления численного построения границ RRC оставалось выбрать один фиксированный размер секрета для основных экспериментов Stage 6.

Проверены четыре значения:

```text
128, 256, 512, 1024 бит
```

Для каждого значения выполнено 8 запусков:

```text
4 промпта × 2 повтора
```

Всего выполнено 32 запуска.

RRC сохраняет отдельный режим с фиксированным секретом: сначала задается размер секрета, а число токенов определяется самим методом. Поэтому этот выбор не превращает RRC в потоковый метод и не меняет правила его оценки.

## 2. Постоянные условия

Во всех четырех группах использовались одинаковые внешние настройки:

```text
model = meta-llama/Llama-3.2-3B
precision_margin = 40
verify_termination = true
temperature = 1.0
top_k = null
top_p = 1.0
max_carrier_tokens = 2048
```

Все группы использовали один `sweep_id`, поэтому сравнение выполнялось в парных условиях по `prompt × replicate`.

## 3. Результаты

| Размер секрета | Медиана токенов | Среднее токенов | Диапазон токенов | Медиана BPT | Средний BPT | Точное восстановление | Сохранение токеновой последовательности | Медиана времени |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 128 | 32.5 | 33.0 | 23–48 | 3.939 | 4.064 | 8/8 | 8/8 | 7.44 с |
| 256 | 66.0 | 68.125 | 47–112 | 3.879 | 3.990 | 8/8 | 8/8 | 14.93 с |
| 512 | 130.0 | 129.125 | 100–167 | 3.941 | 4.054 | 7/8 | 7/8 | 29.81 с |
| 1024 | 256.0 | 253.0 | 197–299 | 4.001 | 4.107 | 7/8 | 7/8 | 57.57 с |

Для всех четырех размеров численная часть RRC остается корректной:

- все 32 запуска завершились;
- обе KL конечны;
- TVD находится на уровне численного нуля;
- случаев повторной потери поддержки распределения не обнаружено.

Следовательно, выбор размера секрета не связан с исправлением численной ошибки. Это только выбор масштаба фиксированного сообщения для основного эксперимента.

## 4. Почему не выбираются 128 или 256 бит

Эти значения дали 8/8 точных полных циклов, но генерируемые тексты слишком короткие для основной сравнительной части:

- 128 бит: медиана 32.5 токена;
- 256 бит: медиана 66 токенов.

Потоковые методы в Pilot B оценивались на 256 токенах. Сравнение RRC на текстах в четыре-восемь раз короче сделало бы оценки качества, времени и надежности менее сопоставимыми по масштабу последовательности.

Кроме того, отсутствие ошибок на коротких текстах нельзя трактовать как доказательство более высокой устойчивости самого RRC. В паре `s5p0003:r02` для 128 и 256 бит генерация заканчивается до позиции 152, на которой в более длинных запусках появляется первое изменение токеновой последовательности после преобразования через текст.

## 5. Почему не выбирается 512 бит

512 бит дают уже более содержательную длину текста — медиана 130 токенов. Однако это примерно половина ориентира потоковых экспериментов.

По BPT и численным метрикам эта точка не дает отдельного преимущества перед 1024 битами:

- медианный BPT: 3.941 против 4.001;
- все KL и TVD в обоих случаях находятся на уровне численного нуля;
- в обоих режимах получено 7/8 точных полных текстовых циклов.

Поэтому 512 бит не дает причины отказываться от более сопоставимой по длине точки 1024 бит.

## 6. Почему выбирается 1024 бита

Для Stage 6 фиксируется:

```text
RRC payload = 1024 bits
precision_margin = 40
```

Основная причина — масштаб генерируемого текста:

```text
median carrier tokens = 256
mean carrier tokens = 253
range = 197..299
```

Это практически совпадает с длиной 256 токенов, использованной для потоковых методов Pilot B, и дает удобную основу для основных сравнений Stage 6.

При этом емкость RRC не ухудшается при увеличении размера секрета:

```text
median BPT = 4.0005
mean BPT = 4.1074
```

Численные метрики также остаются на уровне нуля:

```text
max |forward KL| ≈ 1.34e-16 bits
max |reverse KL| ≈ 1.63e-16 bits
max TVD ≈ 9.99e-17
```

Поэтому 1024 бита дают наиболее подходящий масштаб текста без появления нового численного режима RRC.

## 7. Надежность текстового канала

Для 1024 бит получено 7/8 точных полных циклов. В единственном неточном случае одновременно нарушилось сохранение токеновой последовательности после цепочки:

```text
token IDs → text → retokenization
```

Первое расхождение токенов зафиксировано на позиции 152.

Аналогичная картина в той же паре `s5p0003:r02` наблюдается при размере секрета 512 бит: также 7/8 и первое расхождение на позиции 152.

Эта калибровка сама по себе не выполняла отдельное прямое декодирование `sender_token_ids` для этих двух новых запусков, поэтому здесь не вводится новое причинное утверждение сверх измеренных данных. В Stage 6 нормативной метрикой остается полный текстовый цикл, и результат 7/8 не заменяется на 8/8.

Короткие секреты 128 и 256 бит в этой паре заканчиваются на 48 и 112 токенах соответственно, то есть до позиции 152. Поэтому их 8/8 нельзя использовать как достаточное основание для выбора более короткого сообщения.

## 8. Итоговое решение

Для основных экспериментов Stage 6 фиксируется один режим RRC:

```text
payload_bits = 1024
precision_margin = 40
verify_termination = true
```

RRC по-прежнему оценивается отдельно от потоковых методов:

```text
потоковые методы:
фиксированное число токенов → измеряется переданный секрет

RRC:
фиксированный секрет 1024 бит → измеряется требуемое число токенов
```

Таким образом, 1024 бита не делают экспериментальные режимы одинаковыми по смыслу, но дают близкий масштаб текста: медиана RRC равна 256 токенам.

## 9. Что закрывает эта калибровка

После этого решения для RRC зафиксированы все настройки, необходимые перед Stage 6:

```text
численные границы = Decimal
precision_margin = 40
payload_bits = 1024
```

Отдельный выбор технического режима RRC в Stage 5 считается завершенным.

Следующий шаг Stage 5 относится уже ко всему бенчмарку: определить окончательное число промптов и повторов Stage 6, объем проверки на второй языковой модели и итоговый вычислительный бюджет.
