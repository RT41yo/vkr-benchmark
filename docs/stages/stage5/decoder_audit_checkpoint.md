# Stage 5 — Decoder Audit checkpoint

## 1. Статус

Decoder Audit завершен.

Полный итоговый отчет:

`docs/stages/stage5/decoder_audit_report.md`.

Аудит проводился после Pilot B, в котором из 504 запусков:

- 404 восстановили секрет точно;
- 62 завершились без программной ошибки, но имели `roundtrip_exact=false`;
- 38 завершились `hard failure` во время декодирования.

Цель аудита состояла в том, чтобы отделить возможные ошибки декодеров от ошибок, возникающих при передаче через обычный текстовый канал.

## 2. Прямое декодирование

Для всех конфигураций проверялся путь:

```text
sender token IDs
→ decoder
→ recovered secret
```

Результат: **504/504 exact**.

По методам:

| Метод | Exact |
|---|---:|
| Bins | 96/96 |
| Huffman | 96/96 |
| Arithmetic Coding | 144/144 |
| ADG | 24/24 |
| Discop | 24/24 |
| DAIRstega | 120/120 |

Для 466 исходно завершившихся запусков использовались сохраненные `sender_token_ids`. Для 38 исходных `hard failure` последовательности отправителя были детерминированно восстановлены, поскольку Pilot B не сохранил их после ошибки.

## 3. Независимая проверка декодеров

## 4. 62 случая с неверным секретом

Все 62 случая, где запуск завершился, но `roundtrip_exact=false`, имеют одновременно:

- точное прямое декодирование `sender_token_ids`;
- изменение последовательности после `token IDs → text → retokenization`;
- неверное восстановление по повторно токенизированной последовательности.

Результат: **62/62 связаны с текстовым каналом**.

Агрегированный результат:

`results/stage5/decoder_audit/pilot_b_text_transport_successful_summary.json`.

## 5. 38 hard failure

Для 38 исходных ошибок использовалось детерминированное повторное кодирование исходных конфигураций.

Во всех **38/38** случаях:

- прямой путь уже подтвержден как exact;
- после преобразования в текст и повторной токенизации токены изменились;
- снова возникла ошибка декодирования;
- тип и текст ошибки точно совпали с исходным Pilot B.

Ограничение: исходные `sender_token_ids` этих 38 запусков не были сохранены, поэтому это воспроизведение на восстановленных последовательностях, а не буквальный повтор исходных токенов.

Агрегированный результат:

`results/stage5/decoder_audit/hard_failure_attribution/summary.json`.

## 6. Итог

Аудит не выявил дефектов декодеров.

Причина 100 неточных результатов Pilot B локализована в текстовом канале `token IDs → text → retokenization`. После повторной токенизации одна и та же строка текста может получить другое разбиение на токены. Для токеновой стеганографии это может изменить восстанавливаемые биты и нарушить синхронизацию декодера.

Нормативная метрика end-to-end надежности не меняется: ошибки после текстового канала остаются реальными ошибками Pilot B.

Изменять алгоритмы кодирования или декодирования по результатам аудита не требуется.

Следующий шаг — выбор рабочих точек для Stage 6. RRC остается отдельной задачей Stage 5.
