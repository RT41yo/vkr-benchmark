# Stage 5 — итог проверки численных границ RRC

## 1. Зачем проводилась проверка

Во время калибровки RRC было замечено необычное сочетание результатов:

- `forward KL = +inf` в части запусков;
- обратная KL почти равна нулю;
- TVD находится около нуля;
- секрет при этом восстанавливается точно.

Дополнительная проверка показала, что причина находится не в самом принципе RRC и не в `precision_margin`. Очень маленькие положительные вероятности иногда исчезали при последовательном построении накопительных границ в FP64. После этого соответствующий токен получал интервал нулевой ширины.

Для такого токена выполнялось:

```text
P_reference(token) > 0
Q_stego(token) = 0
```

Поэтому `KL(P_reference || Q_stego)` становилась бесконечной, даже если потерянная вероятность была очень мала.

## 2. Подтверждение причины

Для проверки были повторно исследованы 8 запусков RRC с `precision_margin=40`:

```text
4 промпта × 2 повтора = 8 запусков
payload = 1024 бит
```

Результат:

- в 4 из 8 запусков исходная `forward KL` была бесконечной;
- ровно в этих же 4 запусках найдена потеря положительных интервалов при построении FP64-границ;
- совпадение подтверждено и на уровне запусков, и на уровне отдельных шагов;
- максимальная потерянная вероятность на одном шаге была порядка `10^-15`.

Таким образом, причина `forward KL = +inf` подтверждена экспериментально.

Машиночитаемый результат:

`results/stage5/rrc_boundary_precision_probe/summary.json`

## 3. Что изменено в реализации

После подтверждения причины изменён только способ численного построения границ RRC.

Раньше:

```text
P_reference
→ накопление границ в FP64
→ перевод готовых границ в Decimal
→ RRC
```

Теперь:

```text
P_reference
→ перевод каждой положительной вероятности в Decimal
→ накопление границ в Decimal
→ RRC
```

Также расчёт `Q_stego` больше не восстанавливает ширины интервалов через последовательное FP64-накопление.

Если выбранной Decimal-точности недостаточно и положительная вероятность не может увеличить накопленную границу, запуск завершается с `RRCPrecisionError`. Это лучше, чем незаметно превращать положительный интервал в нулевой.

Смысл RRC, правило вращения, секретная точка, порядок токенов, декодирование и условие завершения не менялись.

## 4. Проверка исправленной реализации

Исправленная реализация была проверена на 8 новых запусках:

```text
precision_margin = 40
payload = 1024 бит
4 промпта × 2 повтора
```

Все 8 запусков завершились без программных ошибок.

Численные результаты:

- конечная `forward KL`: 8/8;
- конечная обратная KL: 8/8;
- максимальная `forward KL`: `1.3798816980502983e-16` бит;
- максимальная обратная KL: `1.63081207823859e-16` бит;
- максимальная TVD: `1.0284529972686038e-16`.

То есть после перехода на Decimal-границы измеренное искажение находится на уровне численной погрешности, а прежний `+inf` исчез полностью.

## 5. Почему общий `validation_gate` равен false

Первичная сводка этой проверки использовала один общий критерий. Он требовал одновременно:

- численной корректности RRC;
- точного восстановления секрета после полного пути через текст.

Поэтому в `summary.json` записано:

```text
validation_gate = false
```

Причина — один из восьми запусков имел `roundtrip_exact=false` и `BER=0.4150390625`.

Это не означает, что исправление численных границ не прошло проверку. Отдельная диагностика этого запуска показала другую причину.

## 6. Разбор единственного неточного запуска

Проблемный запуск:

```text
run_id = 9967d088525fcf46
prompt = s5p0004
replicate = r02
```

Сохранённая последовательность отправителя содержала 249 токенов. После преобразования в текст и повторной токенизации получено 250 токенов.

Первое расхождение появилось на позиции 41.

При декодировании исходных `sender_token_ids` напрямую, без преобразования через текст, RRC восстановил:

```text
1024/1024 бит
BER = 0
roundtrip_exact = true
```

Следовательно, единственный неточный результат полного цикла связан с изменением токеновой последовательности на пути:

```text
token IDs → text → retokenization
```

а не с Decimal-границами RRC и не с ошибкой декодера.

Машиночитаемый результат:

`results/stage5/rrc_decimal_boundary_validation/roundtrip_attribution.json`

## 7. Итог по исправлению RRC

На проверенной выборке получена следующая картина:

- причина старого `forward KL = +inf` установлена;
- потеря поддержки в FP64 устранена;
- 8/8 запусков имеют конечные обе KL;
- KL и TVD находятся около `10^-16`;
- прямое декодирование токенов отправителя корректно;
- 7/8 полных текстовых циклов точны;
- единственный неточный текстовый цикл объяснён повторной токенизацией.

Поэтому численный вопрос построения границ RRC считается закрытым.

`precision_margin=40` остаётся выбранной консервативной настройкой для дальнейших экспериментов. Предыдущая калибровка показала одинаковое поведение при значениях 20, 40 и 60 для арифметики состояния диапазона.

## 8. Что ещё остаётся сделать для Stage 6

RRC пока нельзя полностью считать готовым к окончательному запуску Stage 6 по одной причине: ещё не выбран финальный размер фиксированного секрета.

Следующий отдельный шаг — сравнить:

```text
payload = {128, 256, 512, 1024} бит
```

Цель этого шага — выбрать размер секрета, который даст разумную длину стеготекста и позволит сопоставлять RRC с потоковыми методами по общим метрикам.

Это уже не проверка численной корректности. Численная проблема границ закрыта.
