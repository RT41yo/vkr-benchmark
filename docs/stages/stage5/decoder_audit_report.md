# Stage 5 — итоговый отчет по аудиту декодеров

## 1. Зачем проводился аудит

После Pilot B было получено 504 запуска:

- 404 запуска восстановили секрет точно;
- 62 запуска завершились без программной ошибки, но `roundtrip_exact=false`;
- 38 запусков завершились ошибкой во время декодирования.

Таким образом, 100 из 504 запусков не дали точного восстановления секрета по полному пути:

```text
секрет
→ кодирование
→ sender token IDs
→ text
→ повторная токенизация
→ receiver token IDs
→ декодирование
→ восстановленный секрет
```

На Pilot A уже наблюдались ошибки, связанные с преобразованием `token IDs → text → token IDs`. Однако автоматически переносить этот вывод на Pilot B было нельзя: в Pilot B появились новые проблемные случаи у Arithmetic Coding, ADG и Discop, а часть обратной логики декодеров была реализована в нормализованном бенчмарке самостоятельно.

Поэтому перед выбором рабочих точек Stage 6 нужно было отдельно проверить две вещи:

1. правильно ли декодеры восстанавливают секрет из исходных токенов отправителя;
2. соответствуют ли декодеры алгоритмам статей и авторскому коду, а не только собственным кодерам бенчмарка.

## 2. Проверка прямого декодирования

Для каждого запуска Pilot B проверялся путь без текстового канала:

```text
sender token IDs
→ decoder
→ recovered secret
```

Результат:

| Метод | Точное восстановление |
|---|---:|
| Bins | 96/96 |
| Huffman | 96/96 |
| Arithmetic Coding | 144/144 |
| ADG | 24/24 |
| Discop | 24/24 |
| DAIRstega | 120/120 |
| **Итого** | **504/504** |

Во всех 504 конфигурациях секрет восстанавливается точно, если декодер получает токены отправителя напрямую.

Для 466 запусков, завершившихся без программной ошибки, использовались сохраненные `sender_token_ids`.

Для 38 исходных запусков с ошибкой `sender_token_ids` не были сохранены. Для них последовательность отправителя была детерминированно восстановлена повторным запуском кодирования по исходной конфигурации. Поэтому для этих 38 случаев нельзя сравнить восстановленные токены с потерянной исходной последовательностью побитно. Это ограничение учитывается в дальнейших выводах.

Агрегированный результат прямой проверки хранится в:

`results/stage5/decoder_audit/direct_token_replay/summary.json`.

## 3. Независимая проверка декодеров

Одного результата `504/504` недостаточно: кодер и декодер могли бы содержать одинаковую ошибку и поэтому оставаться взаимно обратными.

Поэтому для всех шести методов была выполнена независимая проверка декодирования на искусственных примерах. Проверочная логика не использовала внутренние вспомогательные функции рабочих реализаций методов.

Проверялись:

- Bins — разбиение словаря на корзины и обратное восстановление битов;
- Huffman — независимое построение дерева и восстановление кода токена;
- Arithmetic Coding — построение целочисленных интервалов, извлечение общего префикса и обновление состояния;
- ADG — обратное восстановление номера группы и битов по алгоритму статьи;
- Discop — последовательное декодирование с независимым эталоном и синхронным состоянием генератора случайных чисел;
- DAIRstega — независимое построение интервалов и обновление состояния диапазона секрета.

Результат:

| Метод | Проверок | Расхождений |
|---|---:|---:|
| Bins | 405 | 0 |
| Huffman | 256 | 0 |
| Arithmetic Coding | 150 | 0 |
| ADG | 994 | 0 |
| Discop | 384 | 0 |
| DAIRstega | 1344 | 0 |
| **Итого** | **3533** | **0** |

Все шесть декодеров прошли независимую проверку.

Результат хранится в:

`results/stage5/decoder_audit/decoder_conformance.json`.

## 4. Разбор 62 запусков с неверно восстановленным секретом

Для 62 запусков, которые завершились без программной ошибки, но имели `roundtrip_exact=false`, были доступны обе последовательности:

- `sender_token_ids` — токены, выбранные кодером;
- `receiver_token_ids` — токены, полученные после преобразования стеготекста обратно в токены.

Для каждого такого запуска одновременно проверялись три факта:

1. исходный Pilot B дал неверное восстановление секрета;
2. прямое декодирование `sender_token_ids` восстановило секрет точно;
3. после текстового канала последовательность токенов изменилась.

Результат:

**62/62 случаев удовлетворяют всем трем условиям.**

По методам:

| Метод | Случаи |
|---|---:|
| Bins | 45/45 |
| Huffman | 9/9 |
| Arithmetic Coding | 7/7 |
| ADG | 1/1 |
| Discop | 0 |
| DAIRstega | 0 |

Первое расхождение токенов возникало в разных местах последовательности:

- минимум — позиция 1;
- медиана — позиция 93;
- максимум — позиция 253.

В типичном случае менялось небольшое число токенов: медиана размера измененного участка равна 2 токенам. При этом даже небольшого изменения иногда достаточно, чтобы декодер начал восстанавливать другие биты.

Отдельно найден один контрольный запуск Bins, в котором `sender_token_ids != receiver_token_ids`, но секрет все равно восстановился точно. Это показывает, что само изменение токенизации не обязательно приводит к ошибке. В 62 проблемных случаях связь подтверждается дополнительным прямым декодированием исходных токенов.

Результаты хранятся в:

- `results/stage5/decoder_audit/pilot_b_text_transport_successful.jsonl`;
- `results/stage5/decoder_audit/pilot_b_text_transport_successful_summary.json`.

## 5. Разбор 38 запусков с ошибкой декодирования

Для 38 исходных `hard failure` последовательности `sender_token_ids` в Pilot B не сохранялись. Поэтому использовался следующий порядок:

```text
исходная конфигурация Pilot B
→ повторное детерминированное кодирование
→ восстановленные sender token IDs
→ text
→ повторная токенизация
→ receiver token IDs
→ decoder
```

Для каждого запуска проверялось:

- прямое декодирование восстановленной последовательности отправителя уже подтверждено как точное;
- текстовый канал изменяет последовательность токенов;
- ошибка декодирования возникает не раньше первого расхождения токенов;
- тип и текст ошибки совпадают с исходной ошибкой Pilot B.

Результат:

| Метод | Воспроизведено |
|---|---:|
| Huffman | 20/20 |
| Arithmetic Coding | 3/3 |
| Discop | 2/2 |
| DAIRstega | 13/13 |
| **Итого** | **38/38** |

Во всех 38 случаях после текстового канала воспроизведена та же ошибка декодирования, что наблюдалась в исходном Pilot B.

Для этих случаев вывод формулируется осторожнее, чем для 62 запусков выше: исходные токены отправителя не были сохранены, поэтому проверка основана на детерминированно восстановленной последовательности, а не на буквальном повторном декодировании потерянных исходных токенов.

Результаты хранятся в:

- `results/stage5/decoder_audit/hard_failure_attribution/hard_failure_attribution.jsonl`;
- `results/stage5/decoder_audit/hard_failure_attribution/summary.json`;
- `results/stage5/decoder_audit/hard_failure_attribution/records/`.

## 6. Итоговый вывод

Аудит не выявил ошибок в декодерах шести потоковых методов в проверенном режиме Pilot B.

Это подтверждается двумя независимыми результатами:

1. все 504 конфигурации восстанавливают секрет точно при прямом декодировании токенов отправителя;
2. все шесть декодеров прошли независимую проверку: 3533 проверки, 0 расхождений.

Причина 100 неточных результатов Pilot B локализована в текстовом канале `token IDs → text → retokenization`:

- для 62 запусков с `roundtrip_exact=false` это подтверждено непосредственно по сохраненным исходным и повторно токенизированным последовательностям;
- для 38 `hard failure` тот же механизм воспроизведен на детерминированно восстановленных последовательностях отправителя, причем во всех случаях совпали тип и текст исходной ошибки.

Основной технический механизм состоит в том, что одна и та же строка текста не обязана сохранять исходное разбиение на токены. После повторной токенизации декодер может получить другую последовательность `token IDs`. Для методов, которые восстанавливают секрет из выбора токенов и состояния языковой модели, этого достаточно для рассинхронизации.

Следовательно, низкая точность полного пути Pilot B не должна интерпретироваться как ошибка самого декодера или как неспособность кодера корректно встроить секрет в исходную последовательность токенов.

При этом нормативная метрика надежности бенчмарка не меняется: полный путь через обычный текстовый канал остается основным условием end-to-end проверки. Поэтому наблюдавшиеся 100 неточных результатов сохраняются как реальные результаты надежности Pilot B, но их причина теперь установлена.

## 7. Статус после аудита

Stage 5 Decoder Audit завершен.

Изменения алгоритмов кодирования и декодирования по результатам аудита не требуются.

Следующий шаг Stage 5 — вернуться к анализу Pilot B и выбору рабочих точек для Stage 6 с учетом установленной причины ошибок надежности.

RRC в этот аудит не входил. Его отдельный вопрос численной точности при построении границ вероятностных интервалов остается самостоятельной задачей Stage 5.
