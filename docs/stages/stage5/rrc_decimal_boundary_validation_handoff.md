# Stage 5 — проверка исправления численных границ RRC

## 1. Что изменено

Предыдущая диагностика показала точную причину `forward KL = +inf` у RRC: очень маленькие положительные вероятности иногда исчезали при последовательном накоплении границ в FP64. В результате для отдельных токенов получалось `P_reference > 0`, но ширина интервала RRC становилась равной нулю.

В этой итерации изменён только численный способ построения интервалов RRC.

Раньше:

```text
P_reference
→ накопление границ в FP64
→ преобразование готовых границ в Decimal
→ range coding
```

Теперь:

```text
P_reference
→ каждая положительная вероятность переводится в Decimal
→ накопление выполняется в Decimal
→ range coding
```

Смысл RRC, порядок токенов, вращение, секретная точка, правило завершения и декодирование не менялись.

## 2. Дополнительная защита

Если выбранной `Decimal`-точности недостаточно даже для сохранения положительной вероятности при накоплении, реализация теперь не продолжает работу с нулевым интервалом. Она явно завершает запуск с `RRCPrecisionError` и сообщает, что требуется увеличить `precision_margin`.

Это нужно, чтобы численная потеря поддержки не оставалась скрытой.

## 3. Расчёт Q_stego

Независимый расчёт `Q_stego` также обновлён.

После перехода границ RRC на `Decimal` ширина интервала токена равна его нормированной положительной вероятности из `P_reference`. Поэтому `Q_stego` теперь строится непосредственно из этих ширин, без повторного последовательного `FP64 cumsum`.

Это изменение относится только к численному представлению распределения и не меняет теоретическое определение `Q_stego` для RRC.

## 4. Что нужно проверить на реальной модели

Подготовлен отдельный небольшой запуск:

`configs/pilots/stage5/rrc_decimal_boundary_validation_llama.json`

Он содержит:

```text
4 промпта × 2 повтора = 8 запусков
payload = 1024 бит
precision_margin = 40
verify_termination = true
top_p = 1.0
top_k = null
```

Используется только один уже выбранный `precision_margin=40`. Повторять `{20,40,60}` не требуется: предыдущая калибровка уже показала plateau для арифметики состояния диапазона.

Новый запуск имеет отдельный `sweep_id`, поэтому ключ RRC будет новым. Это независимая проверка исправленной реализации, а не побитовое повторение старых восьми `margin40` траекторий.

## 5. Критерии успешной проверки

Исправление считается подтверждённым, если одновременно выполняется:

- 8/8 запусков завершились успешно;
- 8/8 секретов восстановлены точно;
- BER = 0 во всех восьми запусках;
- `forward KL` конечна во всех восьми запусках;
- обе KL остаются не больше `1e-12` бит;
- TVD остаётся не больше `1e-12`.

Порог здесь используется как проверка численной погрешности, а не как новая рабочая точка метода.

## 6. Команды

Запуск:

```bash
python scripts/run_stage5_sweep.py \
  configs/pilots/stage5/rrc_decimal_boundary_validation_llama.json \
  --resume
```

После завершения:

```bash
python scripts/summarize_stage5_rrc_decimal_boundary_validation.py
```

Итоговый файл:

`results/stage5/rrc_decimal_boundary_validation/summary.json`

До получения этих восьми результатов исправленная реализация RRC не считается окончательно зафиксированной для Stage 6.

## Итог проверки

Проверка завершена.

Получено:

- 8/8 запусков завершились без программной ошибки;
- обе KL конечны в 8/8;
- максимальная `forward KL` = `1.3798816980502983e-16` бит;
- максимальная TVD = `1.0284529972686038e-16`;
- 7/8 полных текстовых циклов восстановили секрет точно.

Единственный неточный запуск `9967d088525fcf46` был отдельно исследован. Его прямое декодирование по сохранённым `sender_token_ids` восстановило 1024/1024 бита с `BER=0`. Неточность появилась после изменения токеновой последовательности при повторной токенизации текста.

Таким образом, численная проверка Decimal-границ пройдена. Старый общий `validation_gate=false` отражает смешение численной проверки с надёжностью полного текстового канала и не означает дефект исправленного RRC.
