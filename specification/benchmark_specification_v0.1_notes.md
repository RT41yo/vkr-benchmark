# Замечания к `benchmark_specification_v0.1_final.md`

## Назначение документа

Этот документ используется для накопления замечаний, архитектурных уточнений и решений, выявленных в ходе реализации и экспериментальной проверки спецификации бенчмарка v0.1.

`benchmark_specification_v0.1_final.md` при этом остается неизменной как зафиксированный результат этапа 1. Накопленные здесь замечания должны быть рассмотрены при подготовке итоговой спецификации бенчмарка v1.0 на этапе 5.

---

## Замечание 1. Расширить Method adapter API для stateful и fixed-message методов

### Причина

В спецификации v0.1 концептуальный интерфейс Method adapter ориентирован преимущественно на пошаговые методы, для которых на каждом шаге можно явно определить:

- выбранный токен;
- число использованных битов (`bits_consumed`);
- восстановленные на этом шаге биты (`recovered_bits`);
- обновленное состояние метода.

После комплексного изучения реализаций всех выбранных методов выяснилось, что такая модель хорошо подходит для Bins, Huffman, ADG, Discop и в значительной степени Arithmetic Coding, но является слишком узкой для методов типа RRC.

В RRC секретное сообщение рассматривается как единое числовое значение. В процессе генерации последовательно обновляется диапазон и применяется псевдослучайное вращение, однако отдельный токен нельзя однозначно интерпретировать как «потребивший» конкретное число битов сообщения. Аналогично при декодировании секрет восстанавливается не независимо на каждом шаге, а после обработки всей последовательности и выполнения обратных преобразований.

### Предлагаемое изменение для v1.0

В спецификации v1.0 заменить обязательную пошаговую семантику `bits_consumed / recovered_bits` на более общий lifecycle-интерфейс stateful-сессий.

Концептуально:

```text
create_encoder_session(...)
create_decoder_session(...)

encoder.step(P_reference, token_order)
    -> token_id, step_info

encoder.is_finished()

encoder.finalize()
    -> payload_info

decoder.observe(P_reference, token_order, observed_token_id)
    -> step_info

decoder.finalize()
    -> recovered_payload
```

Пошаговые методы при этом должны оставаться частным случаем данного интерфейса: для них `step_info` может содержать число реально использованных или восстановленных битов, а `finalize()` быть тривиальным.

### Требование к реализации до v1.0

Несмотря на то, что спецификация v0.1 остается неизменной, программную архитектуру бенчмарка начиная с этапа 2 следует сразу проектировать с учетом stateful `EncoderSession / DecoderSession`, чтобы последующее подключение RRC и других методов не требовало существенной переделки инфраструктуры.

### Статус

Выявлено при анализе авторских реализаций методов перед началом этапа 2.

Учесть при подготовке `benchmark_specification_v1.0`.

## Замечание 2. Разделить прочитанные secret bits и подтвержденный полезный payload

### Причина

При интеграции Arithmetic Coding выяснилось, что число битов, которые encoder прочитал из `SecretSource`, не обязательно совпадает с числом реально встроенных полезных битов.

Arithmetic Coding поддерживает перекрывающееся `precision`-битное look-ahead окно. Encoder заранее читает биты, необходимые для определения текущей secret point, но полезной нагрузкой становятся только те биты, которые однозначно фиксируются выбранным подинтервалом. Поэтому в fixed-carrier режиме типично выполняется:

```text
secret_bits_read = precision + payload_bits
```

Дополнительные look-ahead биты не должны учитываться в BPT, entropy utilization, BER или `roundtrip_exact` как полезная нагрузка.

### Предлагаемое уточнение для v1.0

Явно различить как минимум два понятия:

- `secret_bits_read` — число битов, фактически запрошенных encoder'ом из secret stream, включая look-ahead/служебное чтение;
- `payload_bits` — число подтвержденных полезных битов, реально встроенных в carrier и подлежащих восстановлению decoder'ом.

Для streaming prefix-методов полезный секрет должен определяться как подтвержденный префикс secret stream длины `payload_bits`. `EncoderFinalization.payload_bits` следует считать авторитетным session-level значением полезной нагрузки.

Если метод предоставляет пошаговый `bits_consumed`, должно выполняться:

```text
sum(bits_consumed_t) = payload_bits
```

Для методов, где такая пошаговая семантика неприменима, например RRC, `bits_consumed_t` может отсутствовать, а payload определяется при `finalize()`.

### Требование к реализации до v1.0

Начиная с AC end-to-end интеграции runner должен отдельно хранить:

```text
read_secret_bits
payload_secret_bits
```

и сравнивать decoder только с `payload_secret_bits`. Прочитанный, но еще не подтвержденный look-ahead не считается полезной нагрузкой.

### Статус

Выявлено при реализации Arithmetic Coding на этапе 2.

Учесть при подготовке `benchmark_specification_v1.0`.

## Замечание 3. Зафиксировать способ вычисления процентилей при наличии `+inf`

### Причина

Спецификация v0.1 требует сохранять `kl_p95_bits` и `tvd_p95`, но не задает
конкретный estimator/метод интерполяции процентиля. Для KL это становится
существенным уже на базовых методах: при направлении
`D_KL(P_reference || Q_stego)` часть или все шаги могут иметь значение `+inf`.
Стандартная линейная интерполяция между конечным числом и `+inf` в некоторых
численных библиотеках дает `NaN`, что недопустимо для воспроизводимого
benchmark result.

### Решение реализации v0.2

На этапе 2 для p95 используется эмпирический **nearest-rank percentile**:

```text
rank = ceil(0.95 * N)
p95 = sorted_values[rank - 1]
```

Такой расчет сохраняет `+inf` как содержательное наблюдение и не создает
искусственное конечное значение или `NaN` интерполяцией.

### Предлагаемое уточнение для v1.0

Явно зафиксировать estimator для всех percentile-полей benchmark schema
(как минимум KL/TVD, а позднее latency/performance), чтобы разные реализации и
версии библиотек не давали разные значения на одном наборе step metrics.

### Статус

Выявлено при реализации KL/TVD на этапе 2, шаг 7.3.

Учесть при подготовке `benchmark_specification_v1.0`.
