# Замечания к `benchmark_specification_v0.1_final.md`

## Назначение документа

Этот документ используется для накопления замечаний, архитектурных уточнений и решений, выявленных в ходе реализации и экспериментальной проверки спецификации бенчмарка v0.1.

`benchmark_specification_v0.1_final.md` при этом остается неизменной как зафиксированный результат этапа 1. Накопленные здесь замечания должны быть рассмотрены при подготовке итоговой спецификации бенчмарка v1.0 на этапе 5.

## Замечание 1. Расширить Method adapter API для stateful и fixed-message методов

### Причина

В спецификации v0.1 концептуальный интерфейс Method adapter ориентирован преимущественно на пошаговые методы, для которых на каждом шаге можно явно определить:

- выбранный токен;
- число использованных битов (`bits_consumed`);
- восстановленные на этом шаге биты (`recovered_bits`);
- обновленное состояние метода.

После комплексного изучения реализаций всех выбранных методов выяснилось, что такая модель хорошо подходит для Bins, Huffman, ADG, Discop и в значительной степени Arithmetic Coding, но является слишком узкой для методов типа RRC.

В RRC секретное сообщение рассматривается как единое числовое значение. В процессе генерации последовательно обновляется диапазон и применяется псевдослучайное вращение, однако отдельный токен нельзя однозначно интерпретировать как «потребивший» конкретное число битов сообщения. Аналогично при декодировании секрет восстанавливается не независимо на каждом шаге, а после обработки всей последовательности и выполнения обратных преобразований.

### Предлагаемое изменение для v1.0

В спецификации v1.0 заменить обязательную пошаговую семантику `bits_consumed / recovered_bits` на более общий lifecycle-интерфейс stateful-сессий.

Концептуально:

```text
create_encoder_session(...)
create_decoder_session(...)

encoder.step(P_reference, token_order)
    -> token_id, step_info

encoder.is_finished()

encoder.finalize()
    -> payload_info

decoder.observe(P_reference, token_order, observed_token_id)
    -> step_info

decoder.finalize()
    -> recovered_payload
```

Пошаговые методы при этом должны оставаться частным случаем данного интерфейса: для них `step_info` может содержать число реально использованных или восстановленных битов, а `finalize()` быть тривиальным.

### Требование к реализации до v1.0

Несмотря на то, что спецификация v0.1 остается неизменной, программную архитектуру бенчмарка начиная с этапа 2 следует сразу проектировать с учетом stateful `EncoderSession / DecoderSession`, чтобы последующее подключение RRC и других методов не требовало существенной переделки инфраструктуры.

### Статус

Выявлено при анализе авторских реализаций методов перед началом этапа 2.

Учесть при подготовке `benchmark_specification_v1.0`.
